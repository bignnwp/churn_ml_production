## 2. Краткое описание роли модели в процессе

### Какую задачу в процессе решает модель

Модель решает задачу **прогнозирования оттока клиентов банка** (бинарная классификация по целевой переменной `Exited`).  
На этапе после feature engineering она по признакам клиента выдаёт класс и/или вероятность ухода. Этот сигнал используется дальше для приоритизации клиентов и планирования мероприятий по удержанию.

### Почему для этой задачи целесообразно использовать ML

- Связь признаков (возраст, география, активность, баланс, число продуктов) с оттоком **нелинейна и многофакторна** — правила «если… то…» плохо масштабируются. Это одна из главных причин, почему здесь хорошо работает машинное обучение, а не простые правила. **Многофакторная** означает, что на решение клиента уйти влияет сразу много признаков одновременно (возраст, география, пол, количество продуктов и другие). При этом признаки работают не по отдельности, а в комбинациях. **Нелинейная** означает, что зависимость не выглядит как прямая линия. То есть **нельзя** сказать: «чем больше баланс — тем меньше вероятность ухода» или «чем старше клиент — тем выше риск» в виде простой формулы.
- Нужно **ранжирование** клиентов по риску, а не только жёсткие пороги: Random Forest даёт вероятности и устойчив к смешанным типам признаков.
- Есть размеченная историческая выборка (`Exited`), что делает supervised learning естественным выбором.
- Дисбаланс классов и необходимость высокого **recall** хорошо обрабатываются через `class_weight` и подбор гиперпараметров под `scoring="recall"`.

### Какие данные поступают на вход модели

1. **Сырые данные:** `data/raw/train.csv` (или путь, переданный в CLI `--data`).
2. После очистки и feature engineering на вход pipeline подаются:
   - **Числовые:** `Age`, `NumOfProducts`, `Balance`, `BalanceToSalary`, `ActiveMultiProduct`, `SegmentFlag`
   - **Категориальные:** `IsActiveMember`, `Geography`, `Gender`, `AgeGroup`
3. Целевая переменная при обучении: `Exited`.  
   Идентификаторы (`id`, `CustomerId`, `Surname`) **не** подаются в модель.

В проде на inference ожидается тот же набор признаков (после того же `add_features` и preprocessor из pipeline).

### Как результат работы модели используется дальше в процессе

1. **Обучение:** лучшая модель и метрики сохраняются; артефакт — `models/churn_random_forest.joblib`.
2. **Review:** затем проверяются метрики, стабильность и соответствие Model Card; при необходимости возвращаюсь к данным/признакам.
3. **Внедрение:** версия модели используется для batch-скоринга клиентов (или интеграции в CRM): на выходе — вероятность/флаг риска оттока. Модель в режиме batch-скоринга применяется не к одному клиенту в реальном времени, а сразу к большому набору клиентов.
4. **Бизнес-использование:** списки клиентов с высоким риском передаются в CRM / retention; модель **не** принимает финальное решение за человека.
5. **Мониторинг и цикл:** при дрейфе данных или падении качества запускается переобучение (возврат к подготовке данных и train).

## 4. Итог

Модель **Churn Random Forest** стоит в центре ML-цикла проекта: от подготовленных признаков клиентов банка до сигнала риска оттока для CRM. ML оправдан сложностью зависимостей и наличием разметки; вход — согласованный набор числовых и категориальных признаков; выход — вероятность/класс, который используется как рекомендация в процессе удержания и подлежит мониторингу с возможностью переобучения.

## 5. Экономический эффект проекта

### Бизнес-контекст

Отток клиентов напрямую влияет на выручку банка. Привлечение нового клиента обычно значительно дороже, чем удержание существующего. Модель позволяет направлять бюджет на удержание в первую очередь на клиентов с высоким риском ухода и за счёт этого повышать эффективность кампаний.

### Оценка эффекта 

Допущения:

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| База клиентов, по которой делается скоринг | 20 000 | пилотный сегмент, не вся база банка |
| Доля клиентов с высоким риском (топ по модели) | 15 % | ≈ 3 000 клиентов |
| Исторический churn rate в этом сегменте | 25 % | выше среднего по базе |
| Средний LTV клиента | 25 000 ₽ | консервативная оценка |
| Стоимость контакта / оффера на 1 клиента | 800 ₽ | звонок, сообщение, небольшой бонус |
| Доля клиентов, которых удаётся удержать | 20 % | реалистичный success rate кампании |
| Recall модели | ≈ 0,65–0,70 | ориентир |

**Расчёт:**

1. Модель выделяет ≈ 3 000 клиентов с высоким риском.
2. Без модели из этого сегмента ушло бы примерно 750 человек (25 %).
3. При success rate 20 % удаётся удержать ≈ 150 клиентов.
4. Сохранённая ценность: 150 × 25 000 ₽ = **3,75 млн ₽** в год.
5. Затраты на кампанию: 3 000 × 800 ₽ = **2,4 млн ₽**.
6. **Чистый эффект ≈ 1,3–1,5 млн ₽** в год на пилотном сегменте.

### Почему эти цифры реалистичны

- Берётся не вся база банка, а пилотный сегмент (20 тыс. клиентов).
- LTV взят консервативно.
- Success rate кампании — 20 % (не завышен).
- Учитываются реальные затраты на контакт.

При масштабировании на большую базу эффект будет расти пропорционально. Даже на пилоте модель уже показывает положительный результат и окупает затраты на разработку и поддержку.

### Как измерять эффект на практике

- A/B-тест: группа со скорингом модели vs контрольная группа.
- Фактический churn rate в скоринговом сегменте.
- Стоимость удержания одного клиента.
- Uplift (разница в доле удержанных).

Эти показатели отслеживаются на этапе мониторинга и помогают принимать решение о дальнейшем использовании модели и её переобучении.
