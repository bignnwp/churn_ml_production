# Model_BPMN: BPMN-схема retraining-цикла модели оттока

**Проект:** `churn_ml_production` (прогноз оттока клиентов банка, Random Forest)  
**Связанный документ:** [Model Card](model_card.md)  
**Файл схемы:** [churn_retraining_cycle.bpmn](bpmn/churn_retraining_cycle.bpmn) — открыть в [bpmn.io](https://demo.bpmn.io/)  
**Инструмент:** [https://bpmn.io/](https://bpmn.io/)

Документ соответствует домашнему заданию модуля «BPMN и Оркестрация жизненного цикла моделей»:

> Создайте BPMN-процесс, включающий: триггер по дрифту → Retraining → Валидацию (User Task) → Сравнение двух моделей (аукцион по AUC) → Деплой лучшей → Уведомление в Telegram.  
> Критерии: полнота, логика, human-in-the-loop.

---

## 1. Назначение процесса

Процесс описывает **замкнутый цикл переобучения** модели Churn Random Forest:

1. Мониторинг обнаруживает дрифт (data / concept / decay метрик) или срабатывает расписание.
2. Автоматически запускается retraining на свежих данных.
3. Аналитик (**User Task**, Human-in-the-loop) валидирует новую модель.
4. Система сравнивает **новую** и **текущую прод**-модель (аукцион по AUC + Recall + F1).
5. Лучшая модель деплоится (или оставляется прод).
6. Команда получает уведомление в Telegram.
7. Процесс возвращается к мониторингу.

BPMN здесь — **исполняемая спецификация** жизненного цикла модели (ModelOps), а не только DAG.

---

## 2. BPMN-диаграмма (дорожки, как в образце)

Схема построена в нотации BPMN 2.0 с **горизонтальными дорожками (lanes)**:

| Дорожка | Кто / что | Задачи |
|---------|-----------|--------|
| **Мониторинг** | Система мониторинга | Start (дрифт/расписание), возврат к мониторингу, End |
| **ML Pipeline** | Автоматизация (Service Task) | Загрузка данных, обучение, запись метрик, сравнение моделей, деплой / оставить прод |
| **Аналитик** | Человек (User Task) | Валидация модели, шлюз «Одобрена?» |
| **Уведомления** | Сервис уведомлений | Telegram при отклонении и по итогу цикла |

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│  Retraining-цикл модели оттока (Churn RF)                                    │
├──────────────┬───────────────────────────────────────────────────────────────┤
│ Мониторинг   │  ○ Дрифт / расписание  ···  [Вернуться к мониторингу] ─○ Конец│
├──────────────┼───────────────────────────────────────────────────────────────┤
│ ML Pipeline  │  ⚙ Загрузить данные → ⚙ Обучить новую модель → ⚙ Записать     │
│              │    метрики                                                    │
│              │         ⚙ Сравнить модели (аукцион AUC) → ◇ Новая лучше?      │
│              │                    да ↘              ↙ нет                    │
│              │              ⚙ Деплой новой      ⚙ Оставить прод-модель        │
├──────────────┼───────────────────────────────────────────────────────────────┤
│ Аналитик     │              👤 Валидация модели → ◇ Одобрена?                │
│              │                         да ↗        ↘ нет                     │
├──────────────┼───────────────────────────────────────────────────────────────┤
│ Уведомления  │     ⚙ Telegram: модель отклонена    ⚙ Telegram: результат     │
└──────────────┴───────────────────────────────────────────────────────────────┘
```

**Обозначения (как на учебной схеме-образце):**

| Символ | Элемент BPMN |
|--------|----------------|
| ○ | Start Event / End Event |
| 👤 | User Task (человек в процессе) |
| ⚙ | Service Task (автоматизация) |
| ◇ с X | Exclusive Gateway (выбор одной ветки) |
| да / нет | Подписи на исходящих потоках из шлюзов |

## 4. Таблица элементов BPMN

| № | Элемент | Тип | Дорожка | Описание |
|---|---------|-----|---------|----------|
| 1 | Дрифт / расписание | Start Event | Мониторинг | PSI > 0.25, KS, падение Recall или timer |
| 2 | Загрузить данные | Service Task | ML Pipeline | `data.py` + `features.py` |
| 3 | Обучить новую модель | Service Task | ML Pipeline | `train.py` → `models/churn_rf_vN.joblib` |
| 4 | Записать метрики | Service Task | ML Pipeline | recall, precision, f1, roc_auc, average_precision |
| 5 | Валидация модели | **User Task** | Аналитик | Роль `model_validator`, Approve / Reject |
| 6 | Одобрена? | Exclusive Gateway | Аналитик | да → сравнение; нет → Telegram «отклонена» |
| 7 | Сравнить модели (аукцион AUC) | Service Task | ML Pipeline | new vs production по AUC + Recall + F1 |
| 8 | Новая лучше? | Exclusive Gateway | ML Pipeline | да → деплой; нет → оставить прод |
| 9 | Деплой новой модели | Service Task | ML Pipeline | публикация артефакта в prod |
| 10 | Оставить прод-модель | Service Task | ML Pipeline | фиксация решения |
| 11 | Telegram: модель отклонена | Service Task | Уведомления | webhook при Reject |
| 12 | Telegram: результат цикла | Service Task | Уведомления | версия, метрики, решение |
| 13 | Вернуться к мониторингу | Service Task | Мониторинг | замыкание цикла |
| 14 | Конец | End Event | Мониторинг | завершение экземпляра |

## 5. Human-in-the-loop

| Что | Как |
|-----|-----|
| **User Task** | «Валидация модели» — обязательный ручной шаг до аукциона и деплоя |
| **Роль** | `model_validator` (аналитик / DS) |
| **Форма** | Метрики новой модели, сравнение с baseline, кнопки «Одобрить» / «Отклонить + комментарий» |
| **SLA** | < 24 ч; при просрочке — эскалация (опционально Timer Boundary Event) |
| **Аудит** | Кто, когда, решение и комментарий пишутся в лог процесса |

Без User Task критерий **human-in-the-loop** не выполняется.

---

## 6. Условие на шлюзе «Новая лучше?» (несколько метрик)

Не только AUC — целостная оценка (из конспекта вебинара):

```text
IF (AUC_new > AUC_prod)
   AND (Recall_new >= Recall_prod - 0.02)
   AND (F1_new >= F1_prod - 0.02)
THEN деплой новой
ELSE оставить прод-модель
```

Для churn **recall** критичен: пропуск уходящего клиента обычно дороже ложного срабатывания.

---

## 7. Триггер по дрифту

| Тип | Признак | Пример условия Start |
|-----|---------|----------------------|
| Data drift | PSI / KS по Age, Balance, Geography, … | PSI > 0.25 |
| Concept drift | Смена связи X → Exited | Падение ROC-AUC / Recall на свежей выборке |
| Accuracy decay | Метрики на prod | Recall < baseline − δ |

Start Event: Message (от мониторинга) или Timer (регулярный чек).

## 8. Уведомление в Telegram

Service Task → HTTP POST (webhook / Bot API):

```json
{
  "chat_id": "<team_chat>",
  "text": "Churn RF cycle finished.\nDecision: DEPLOY v0.2.0\nAUC_new=0.87 vs AUC_prod=0.84\nRecall_new=0.71\nValidator: @analyst\nModel Card: docs/model_card.md"
}
```

При отклонении — отдельное сообщение с причиной из комментария User Task.

## 9. Как открыть и сдать схему

1. Скачать [churn_retraining_cycle.bpmn](bpmn/churn_retraining_cycle.bpmn).

4. **Export as PNG/SVG** → положить в `docs/bpmn/`.
5. В сдаче указать ссылки на:
   - `docs/Model_BPMN.md`
   - `docs/bpmn/churn_retraining_cycle.bpmn` (и PNG)

---

## 11. Защита от бесконечного цикла

- Process variable `retrain_count`, максимум 3 подряд.
- Если метрики не растут — User Task «Анализ причины дрифта» (остановка авто-цикла).
- Каждое решение (Approve/Reject, Deploy/Keep) логируется для аудита.
