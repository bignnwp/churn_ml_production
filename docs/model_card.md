## 1. Model Details

| Поле | Значение |
|------|----------|
| **Название** | Churn Random Forest |
| **Версия** | 0.1.0 |
| **Тип** | Random Forest Classifier (sklearn) |
| **Задача** | Бинарная классификация |
| **Целевая переменная** | `Exited` (0 — клиент остаётся, 1 — клиент ушёл) |
| **Язык / фреймворк** | Python 3, scikit-learn, imbalanced-learn |
| **Дата** | 2026 |
| **Владелец / проект** | `churn_ml_production` |

Модель предсказывает вероятность оттока клиента банка по признакам из CRM/транзакционных данных.

Артефакт обучения сохраняется через `joblib` (по умолчанию `models/churn_random_forest.joblib`).

---

## 2. Intended Use

### Основное назначение

- Выявление клиентов с повышенным риском ухода (`Exited = 1`).
- Формирование приоритизированных списков для CRM и команд удержания.
- Поддержка решений по retention-кампаниям и анализу факторов оттока.

### Предполагаемые пользователи

- Аналитики и data scientists банка.
- Специалисты CRM / customer success.
- Менеджеры по продуктам и удержанию клиентов.

### Вне области применения (out-of-scope)

- Единственный источник решения по конкретному клиенту (кредит, закрытие счёта, персональные санкции и т.п.).
- Автоматическое применение без человеческого review.
- Прогноз для клиентов, чьи признаки сильно отличаются от обучающей выборки (другая география, другой продуктовый микс без дообучения).
- Использование как «чёрный ящик» без учёта ограничений по данным и метрикам.

---

## 3. Factors

### Релевантные факторы

- **География** (`Geography`): France, Spain, Germany — распределение оттока может отличаться.
- **Пол** (`Gender`).
- **Возраст и возрастные группы** (`Age`, `AgeGroup`).
- **Активность** (`IsActiveMember`), число продуктов (`NumOfProducts`).
- **Баланс и отношение баланса к зарплате** (`Balance`, `BalanceToSalary`).
- **Производные флаги**: `ActiveMultiProduct`, `SegmentFlag` (сегмент Germany + Female + неактивный + 1 продукт).

### Возможные источники смещения (bias)

- Дисбаланс классов: отток обычно реже, чем «остался» → при обучении используется `class_weight` и при необходимости SMOTE (в pipeline заложен, в текущем train — без SMOTE, с `class_weight`).
- Исторические данные могут отражать прошлые политики банка, а не текущее поведение клиентов.
- Признаки вроде Geography/Gender могут коррелировать с оттоком, но не должны использоваться для дискриминационных решений.

## 4. Metrics

При обучении и оценке считаются:

| Метрика | Назначение |
|---------|------------|
| **Recall** | Основная метрика оптимизации (`scoring="recall"`) — доля реально ушедших, которых модель поймала |
| **Precision** | Доля «предсказанных уходов», которые действительно ушли |
| **F1** | Баланс precision и recall |
| **ROC-AUC** | Качество ранжирования по вероятности |
| **Average Precision (PR-AUC)** | Устойчивее ROC-AUC при сильном дисбалансе классов |

Гиперпараметры Random Forest подбираются через `HalvingRandomSearchCV` (stratified CV).  
Итоговые значения метрик выводятся при запуске `python -m churn_ml.train` и зависят от конкретной выборки `train.csv`.

**Рекомендация по порогу:** порог классификации (по умолчанию 0.5) можно сдвигать в сторону более высокого recall, если цена пропуска уходящего клиента выше, чем ложного срабатывания.

## 5. Evaluation Data

- Источник: файл `data/raw/train.csv` (целевая колонка `Exited`).
- Разделение: stratified train/test split (`test_size=0.2`, `random_state=42`).
- Валидация при подборе гиперпараметров: Stratified K-Fold (`cv_splits=3`).
- Идентификаторы (`id`, `CustomerId`, `Surname`) удаляются до обучения и не участвуют в признаках.

Метрики на test-части считаются после `refit` лучшей модели.

---

## 6. Training Data

### Предобработка

1. Загрузка CSV, удаление идентификаторов.
2. Feature engineering (`add_features`):
   - `AgeGroup` — возрастные бины;
   - `BalanceToSalary` — отношение баланса к зарплате;
   - `ActiveMultiProduct` — активный клиент с ≥2 продуктами;
   - `SegmentFlag` — риск-сегмент (Germany, Female, неактивный, 1 продукт).
3. Числовые признаки: median impute + RobustScaler.
4. Категориальные: most_frequent impute + OneHotEncoder (`drop="first"`, `handle_unknown="ignore"`).

### Признаки, подаваемые в модель

**Числовые:** `Age`, `NumOfProducts`, `Balance`, `BalanceToSalary`, `ActiveMultiProduct`, `SegmentFlag`  

**Категориальные:** `IsActiveMember`, `Geography`, `Gender`, `AgeGroup`

### Алгоритм

- `RandomForestClassifier` внутри `imblearn`/`sklearn` Pipeline.
- Поиск: `HalvingRandomSearchCV` по `n_estimators`, `max_depth`, `min_samples_leaf/split`, `max_features`, `bootstrap`, `class_weight`.
- `class_weight`: `balanced` / `balanced_subsample` (учёт дисбаланса).

## 7. Quantitative Analyses

Количественные результаты зависят от конкретной версии `train.csv` и фиксируются при каждом запуске обучения (stdout + при необходимости отчёты в `reports/`).

Типичный фокус анализа:

- Сравнение recall vs precision на test.
- PR-кривая и ROC-кривая.
- Важность признаков (feature importance Random Forest) для интерпретации.
- Стабильность метрик по fold’ам CV.

При заметном падении recall/ROC-AUC на свежих данных следует инициировать цикл переобучения (см. BPMN).

## 8. Ethical Considerations

- Модель не должна быть единственным основанием для отказа в услуге, изменения тарифа или иных неблагоприятных действий в отношении клиента.
- Признаки, связанные с защищёнными характеристиками (пол, косвенно география), требуют осторожного использования и аудита на fairness.
- Рекомендуется периодический мониторинг fairness (разница метрик по группам Geography/Gender) и документирование решений по порогу.
- Персональные данные клиентов должны обрабатываться в соответствии с политикой банка и применимым законодательством (хранение, доступ, удаление).

## 9. Caveats and Recommendations

### Ограничения

- Качество прогноза зависит от полноты и актуальности признаков в `train.csv`; отсутствие или дрейф признаков ухудшает результат.
- Модель обучена на историческом срезе; изменение продуктовой линейки, макроусловий или политики банка может вызвать concept drift.
- Текущая версия — offline batch-прогноз; online-serving и мониторинг в проде требуют отдельной инфраструктуры.
- В pipeline предусмотрен SMOTE, но в основном сценарии обучения (`train_random_forest`) SMOTE по умолчанию выключен; дисбаланс компенсируется `class_weight`.

### Рекомендации по эксплуатации

1. Перед внедрением новой версии — review метрик и сравнение с предыдущей (см. процесс в [Model_BPMN.md](Model_BPMN.md)).
2. Фиксировать версию модели, seed, данные и гиперпараметры (артефакт + логи обучения).
3. Мониторить долю положительных предсказаний, recall на размеченных свежих кейсах и распределение входных признаков.
4. Переобучать при существенном дрейфе данных или падении бизнес-метрик удержания.
5. Использовать выход модели (вероятность / класс) как сигнал для CRM, а не как автоматическое действие.
